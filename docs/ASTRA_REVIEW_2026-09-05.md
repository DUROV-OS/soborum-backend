## Что проверить перед переносом

1. Backend и frontend — согласованная пара. Сначала подготовить и проверить backend, затем frontend. Никаких новых миграций схемы в пакете нет.
2. Настроить `.env` по обновлённому примеру. `JWT_SECRET` — уникальный секрет не короче 32 символов. `CORS_ALLOWED_ORIGINS` — фактические origins интерфейса. В production wildcard запрещён. `ENVIRONMENT=production`; dev reload по умолчанию отключён.
3. У существующего PostgreSQL volume переменная `POSTGRES_PASSWORD` сама не меняет пароль. Использовать корректный секрет и соответствующий `DATABASE_URL`; не подменять рабочую базу новой пустой базой.
4. `ADMIN_PASSWORD` создаёт только первого администратора и **не меняет пароль существующего**. Известные временные пароли существующих учётных записей необходимо заменить отдельно через администраторский процесс до публикации. В чат секреты не отправлять.
5. После обновления все старые JWT потребуют нового входа. Проверить вход, смену пароля через существующий `PATCH /api/auth/users/{id}` и отклонение старого токена.
6. Для новой установки сначала заполнить сильный `ADMIN_PASSWORD`. Для существующей установки без bootstrap он может быть пустым. Ограничение bcrypt: минимум 12 символов, максимум 72 байта UTF-8.
7. Frontend по умолчанию использует `/api` на своём origin. В dev Vite проксирует `/api` и `/files` на `127.0.0.1:8000`. Если API работает на другом адресе/порту, явно установить `VITE_API_BASE`, например локальный адрес порта 8005 из Compose. В production нужен корректный reverse proxy и SPA fallback для BrowserRouter.
8. Проверить режимы существующих AI-чатов: `auto_approve` теперь исполняется с подтверждением. Сотрудник без admin не получит общий MCP; это сознательное ограничение, а не ошибка подключения.
9. `ANTHROPIC_API_KEY` и доступность настроенной модели нужно проверить на staging с реальным провайдером. Наличие ключа в конфигурации не означает успешную связь. Сводка «Сегодня» от этого не зависит.
10. Перед включением боевых действий повторить проверки конкурентности на PostgreSQL, сценарии полного цикла заказа и проверку отката на копии данных. Откат production этим проходом не проверялся.

## Проверки этого прохода

- Исходный frontend собирался до изменений. Обновлённый frontend также проходит `npm run build`.
- В backend добавлены 34 проверки. `python -m pytest -q` проходит на SQLite и синтетических данных, без вызовов реального AI. Проверяются права, вход, сроки действия пароля, подтверждения, транзакционный откат, список производств, сводка, обрезанный ответ и недоступный провайдер.
- Восемь основных регрессий проверяются на исходном backend и после исправлений, включая две сессии с устаревшим объектом подтверждения. Это не нагрузочный тест конкурентных PostgreSQL-транзакций.
- В frontend подготовлены восемь сценариев Playwright (`tests/smoke.mjs`): production-only, запрет admin, сводка без AI и черновик Марины, очистка формы, ошибка прав, выход, мобильная компоновка, отсутствие демо-паролей в production JS. Проверена синтаксическая корректность сценария; браузерные сценарии в этой среде **не выполнены**: загрузка Chromium не завершилась, облачный браузер не открыл локальный адрес. Скриншоты не выдаются за выполненную приёмку.
- В сборке остаётся предупреждение Vite о JS chunk более 500 kB. Backend выводит предупреждения устаревания текущих Starlette/passlib/FastAPI API. Это не ошибки сборки или тестов; обновления зависимостей и разделение кода не включены в этот пакет.

## Оставшиеся ограничения — не считать закрытыми

| Приоритет | Подтверждённое по исходникам ограничение | Следующее необходимое изменение |
| --- | --- | --- |
| P0 | В `app/warehouse/service.py::approve_request` нет защиты от выдачи сверх остатка; складские изменения также требуют проверки конкурентности и идемпотентности | Единый транзакционный складской сервис для REST и AI, проверка доступного остатка и положительных/конечных количеств, тесты параллельных выдач/поставок на PostgreSQL |
| P0 | Права в основном «admin/worker + раздел». Доступ к разделу не разделяет создание, утверждение и проведение | Матрица должностей и действий, ограничения на конкретные записи и суммы, разделение исполнителя и утверждающего; серверные проверки всех REST и AI-путей |
| P0 | Полноценная бухгалтерия и зарплата в этих репозиториях отсутствуют | Отдельный контролируемый сквозной процесс: документ → сверка → начисление/обязательство → утверждение → проведение. Исключить двойные начисления, добавить сторно и сверку |
| P0 | Приём PDF/изображений в AI-чат не является структурированным OCR с бухгалтерским проведением | Схема извлечённых полей, ссылка на оригинал, уверенность по полям, дубли, ручная проверка и только затем проводка |
| P0 | Совет директоров и сводные инструменты имеют собственные пути доступа к данным и изменениям | Провести их через общую серверную политику; отдельно проверить доступность контекста производства и кадровых данных сотрудникам |
| P1 | Журнал здесь использует существующие `ai_messages` и `ai_pending_actions`, а не независимое неизменяемое хранилище | Append-only аудит с actor, источником, версией политики, решением, результатом и корреляцией со сквозным событием; отдельное архивирование чатов |
| P1 | Нет персонального доступа к документам общей базы знаний | ACL по сотруднику/роли/документу и проверка доступа до передачи контекста модели; затем вернуть MCP сотрудникам |
| P1 | У JWT нет отдельных серверных записей сессий/refresh-token, индивидуального отзыва и rate limiting входа | Серверные сессии, выборочный logout/revoke, ограничение попыток, аудит входа |
| P1 | Часы экономии и стоимость полезного результата пока не измеряются | Ввести исходное время ручного сценария и фактическое подтверждённое время/стоимость результата; не рисовать вымышленные KPI |

Этот пакет — исправления существующего приложения и минимальная серверная политика A0/A2. Он не объявляет готовыми полноценный Guardian, Durov Knowledge, бухгалтерию, зарплату, offline-first или производственный пилот.
