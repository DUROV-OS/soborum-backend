# Разведка МойСклад — модель бухгалтерии и движения денег

> Задача `backlog/PROCESS/0011-b-moysklad-accounting-research.md`
> (дочерняя к `0011-accounting-money-movement.md`).
>
> Цель: зафиксировать, как учёт денег устроен в **МойСклад JSON API 1.2**, чтобы
> модель `MoneyMovement` в Durov OS (`0011-c`) ссылалась на конкретные сущности и
> поля МойСклад, а не на «как удобно».
>
> Источники: официальная дока `https://dev.moysklad.ru/doc/api/remap/1.2/`
> и её исходники `github.com/moysklad/api-remap-1.2-doc` (`md/documents/*`,
> `md/dictionaries/*`, `md/reports/*`). Имена сущностей и полей приведены дословно
> так, как в API.

## 1. Документы движения денежных средств

В МойСклад нет отдельной сущности «проводка». Движение денег — это **финансовые
документы**. Каждый из них — приход или расход, безнал или нал:

| Сущность API | Русское имя | Направление | Канал | Назначение |
|---|---|---|---|---|
| `paymentin` | Входящий платёж | приход (+) | безнал (банк) | деньги пришли на расчётный счёт: оплата от клиента, возврат от поставщика |
| `paymentout` | Исходящий платёж | расход (−) | безнал (банк) | деньги ушли со счёта: оплата поставщику, налоги, **выплата зарплаты**, аренда |
| `cashin` | Приходный ордер | приход (+) | нал (касса) | деньги пришли в кассу |
| `cashout` | Расходный ордер | расход (−) | нал (касса) | деньги выданы из кассы (в т. ч. зарплата наличными) |
| `counterpartyadjustment` | Корректировка взаиморасчётов | ± | — | ручная правка баланса контрагента/сотрудника без реального движения денег |
| `prepayment` / `prepaymentreturn` | Предоплата / возврат предоплаты | ± | — | розница: предоплата по заказу и её возврат |
| `retaildrawercashin` / `retaildrawercashout` | Внесение/выплата (розн. смена) | ± | нал (ДС розницы) | движение по денежному ящику розничной смены |

Для контура Durov OS релевантны первые четыре. Различие нал/безнал (`cashin`/`cashout`
против `paymentin`/`paymentout`) у нас **не воспроизводим** — в Durov OS денежный
контур один. Берём объединённую семантику: «приход» ↔ `paymentin`/`cashin`,
«расход» ↔ `paymentout`/`cashout`.

### 1.1. Ключевые поля денежного документа (дословно из API)

Общие для `paymentin` / `paymentout` / `cashin` / `cashout`:

| Поле | Тип | Смысл |
|---|---|---|
| `sum` | Float | Сумма платежа **в копейках**, в валюте документа. `+Обязательное при ответе` |
| `vatSum` | Float | Сумма НДС (в копейках). `+Обязательное при ответе` |
| `rate` | Object | Валюта + курс (`{currency: Meta, value, ...}`). `+Обязательное при ответе` |
| `moment` | DateTime | Дата документа. `+Обязательное при ответе` |
| `applicable` | Boolean | **Отметка о проведении** (см. §2). `+Обязательное при ответе` |
| `state` | Meta → `state` | Пользовательский статус документа (см. §2). `+Expand` |
| `agent` | Meta | Контрагент. Для `paymentout`/`cashout` — «контрагента, **сотрудника** или юр.лицо». `+Обязательное при создании` |
| `organization` | Meta | Своё юрлицо (от кого/кому). `+Обязательное при создании` |
| `paymentPurpose` | String | Назначение платежа (текст). |
| `operations` | Array(Meta) + `linkedSum` | Привязка платежа к базовым документам (§4.3). |
| `project` | Meta → `project` | Проект — аналитический разрез (§5). `+Expand` |
| `contract` | Meta → `contract` | Договор (§5). `+Expand` |
| `owner` | Meta → `employee` | **Владелец (Сотрудник)** — кто завёл документ. `+Expand` |
| `group` | Meta | Отдел. |
| `name` | String | Номер документа. |
| `description` | String(4096) | Комментарий. |
| `created` / `updated` / `deleted` | DateTime | Служебные даты. `+Только для чтения` |

Только у **безналичных** (`paymentin` / `paymentout`):

| Поле | Тип | Смысл |
|---|---|---|
| `organizationAccount` | Meta → `account` | Расчётный счёт своего юрлица. `+Expand` |
| `agentAccount` | Meta → `account` | Расчётный счёт контрагента. `+Expand` |
| `incomingNumber` | String(255) | Входящий номер (номер платёжного поручения). |
| `incomingDate` | DateTime | Входящая дата. |

Только у **расходных** (`paymentout` / `cashout`):

| Поле | Тип | Смысл |
|---|---|---|
| `expenseItem` | Meta → `expenseitem` | **Статья расходов / статья ДДС** (§3). Обязательна при проведении. |
| `noClosingDocs` | Boolean | «Без закрывающих документов». |

> У приходных (`paymentin` / `cashin`) поля `expenseItem` **нет** — доход в МойСклад
> не разбивается по статье расхода; его «вид» определяется типом документа и
> привязкой `operations` (к какому заказу/отгрузке относится приход).

Только у `paymentin` / `cashin`: `factureOut` (счёт-фактура выданный);
у `paymentout` / `cashout`: `factureIn` (счёт-фактура полученный).

## 2. Проведение (`applicable`) против статуса (`state`)

Это два **независимых** признака — ключевой факт для статусной машины `0011-c`.

- **`applicable`** (Boolean) — «Отметка о проведении».
  - `false` → документ существует как **черновик**: он не влияет на остаток денег
    и не двигает взаиморасчёты.
  - `true` → документ **проведён**: сумма учтена в остатке ДС, баланс контрагента
    (или сотрудника) пересчитан, приход/расход попал в отчёты (ДДС, «Прибыли и
    убытки»).
  - Это переключаемый флаг: провёл → распровёл. Отдельного значения «отменён» у
    документа нет — «отмена» в МойСклад = либо распроведение (`applicable=false`),
    либо удаление (`deleted`), либо компенсирующая `counterpartyadjustment`.
- **`state`** (Meta → сущность `state`) — **пользовательский статус** документа из
  настраиваемого списка (например «Ожидает оплаты», «Оплачен», «Согласование»).
  У `state` есть `stateType` (`Regular` / `Successful` / …), `name`, `color`,
  `entityType`. `state` — это визуально-процессный ярлык; **сам по себе денег не
  двигает**, двигает только `applicable`.

### 2.1. Проекция на статусную машину `MoneyMovement` (`0011-c`)

Родитель `0011` задаёт: `draft → approved → posted → cancelled` (только вперёд +
`cancelled`; `posted` не редактируется).

| Статус Durov OS | Эквивалент в МойСклад |
|---|---|
| `draft` | документ создан, `applicable = false`, `state` = «Черновик»/«Согласование» |
| `approved` | `applicable = false`, `state` = «Согласовано» (согласование в Durov OS — это наш слой поверх `state`; в МойСклад отдельного шага нет) |
| `posted` | `applicable = true` — проведён, деньги/взаиморасчёты учтены; редактирование запрещаем (в МойСклад проведённый редактируется, но мы ужесточаем — см. принцип PROJECT.md «оплата — независимое состояние») |
| `cancelled` | `applicable = false` + пометка причины; при уже проведённом — компенсирующая запись по образцу `counterpartyadjustment`, исходный документ не удаляем (история не переписывается) |

Вывод: **`applicable` — это граница `posted`**. Шаги `draft`/`approved` — наш
процессный слой (аналог `state` + задача на согласование из раздела `tasks`).

## 3. Статьи движения денежных средств (`expenseitem`)

Сущность API — `expenseitem`, русское имя «Статья расходов». В интерфейсе МойСклад
это статьи для отчётов «ДДС» и «Прибыли и убытки».

### 3.1. Поля `expenseitem`

| Поле | Тип | Смысл |
|---|---|---|
| `name` | String(255) | Наименование статьи. `+Обязательное при ответе` `+Необходимо при создании` |
| `description` | String(4096) | Описание. |
| `code` / `externalCode` | String(255) | Коды. |
| `operatingExpenses` | Boolean | **Учитывать ли в оценке прибыли**. По умолчанию `true`. Если `false` — расход по статье не попадает в «Прибыли и убытки» (пример встроенных: «Возврат», «Перемещение»). |
| `group` | Meta | Отдел сотрудника (для пользовательских статей). |
| `owner` | Meta → `employee` | Владелец. |
| `shared` | Boolean | Общий доступ. |
| `id` / `meta` / `accountId` / `updated` | — | Служебные. |

### 3.2. Встроенные статьи (из ответа API `GET /entity/expenseitem`)

`Закупка товаров` · `Возврат` (`operatingExpenses:false`) · `Налоги и сборы` ·
`Списания` · `Перемещение` (`operatingExpenses:false`) · `Аренда` · `Зарплата` · …
Плюс пользовательские статьи с произвольными `name`.

### 3.3. Проекция на `MoneyMovement.kind` (`0011-c`)

`kind` в Durov OS = **направление (приход/расход) + подвид**. Подвид берём как
короткий фиксированный enum, смысловые ярлыки — из статей ДДС МойСклад:

| `MoneyMovement` подвид | Направление | Статья ДДС МойСклад | Привязка `source_ref` |
|---|---|---|---|
| `sale_income` — доход от продажи | приход | (у прихода статьи нет; тип = `paymentin`/`cashin` + `operations` на счёт/отгрузку клиента) | `client_id` |
| `salary_payout` — выплата зарплаты | расход | `Зарплата` | `employee_id` |
| `supply_payment` — оплата поставки | расход | `Закупка товаров` | `supply_id` |
| `tax` — налоги | расход | `Налоги и сборы` | — |
| `rent` — аренда | расход | `Аренда` | — |
| `other` — прочее | приход/расход | пользовательская статья | — |

Набор можно расширять; хранить подвид строкой/enum, а «человеческую» статью —
отдельным справочником по образцу `expenseitem` (`name` + `operatingExpenses`),
если Арсений захочет настраиваемые статьи. Для MVP `0011-c` — фиксированный enum
выше.

## 4. Контрагенты и взаиморасчёты

### 4.1. `counterparty` (Контрагент)

Единый справочник покупателей и поставщиков. Ключевые поля:

| Поле | Тип | Смысл |
|---|---|---|
| `name` | String | Наименование. |
| `companyType` | Enum | Тип: юрлицо / ИП / физлицо — от него зависит набор реквизитов. `+Обязательное` |
| `accounts` | MetaArray → `account` | Банковские счета контрагента. `+Expand` |
| `contactpersons` | MetaArray | Контактные лица. |
| `salesAmount` | Int | **Сумма продаж** контрагенту (в копейках). `+Только для чтения` |
| `bonusPoints` | Int | Бонусные баллы. `+Только для чтения` |
| `state` | Meta → `state` | Статус контрагента (воронка). |
| `tags` | Array(String) | Метки. |
| `inn` / `kpp` / `ogrn` / `legalTitle` / `legalAddress` … | String | Реквизиты (в подобъекте по `companyType`). |
| `email` / `phone` / `fax` / `actualAddress` | String | Контакты. |
| `archived` | Boolean | В архиве. |

> Баланс/долг **не хранится полем на `counterparty`** — он вычисляется отчётом
> (см. §4.2). `salesAmount` — это оборот, не задолженность.

### 4.2. Отчёт «Показатели контрагентов» (`report/counterparty`)

`GET /report/counterparty` (право `viewCompanyCRM`). Поля показателя:

| Поле | Тип | Смысл |
|---|---|---|
| `balance` | Float | **Баланс взаиморасчётов** (в копейках). Знак: `> 0` — контрагент должен нам, `< 0` — мы должны контрагенту. |
| `averageReceipt` | Float | Средний чек. |
| `bonusBalance` | Float | Баллы. |
| `profit` | Float | Прибыль (право `viewProductCostAndProfit`). |
| `lastEventDate` / `lastDemandDate` / … | DateTime | Даты последних операций. |

Баланс = свёртка всех проведённых документов реализации/закупки и платежей по
контрагенту. Меняется **только при `applicable = true`**.

### 4.3. Как платёж влияет на взаиморасчёты — поле `operations`

В `operations` кладут `meta` базовых документов, к которым привязан платёж, с
полем `linkedSum` (сколько денег платежа отнести на этот документ). Базовые
документы: `customerorder` (заказ покупателя), `demand` (отгрузка),
`invoiceout` (счёт покупателю), `purchaseorder` (заказ поставщику),
`supply` (приёмка), `invoicein` (счёт поставщика), `commissionreportin/out`.

- Платёж **с** `operations` → закрывает конкретную реализацию/закупку
  (уменьшает долг по ней).
- Платёж **без** `operations` → просто аванс/переплата, оседает в общем балансе
  контрагента.

### 4.4. `counterpartyadjustment` (Корректировка взаиморасчётов)

Ручная правка баланса без реального движения денег. Поля: `agent`
(**контрагент или сотрудник**), `organization`, `sum` (в копейках,
`+Только для чтения`), `moment`, `applicable`, `description`. Применение в
Durov OS: реализация «отмены проведённой проводки с основанием» и разовых
списаний/начислений долга.

### 4.5. Выплата сотруднику

Отдельной сущности «зарплатный документ» в API нет. Выплата зарплаты — это
`paymentout` (или `cashout`) с:

- `agent` = `meta` **сотрудника** (`employee`), не контрагента (для расходных
  документов `agent` допускает «контрагента, сотрудника или юр.лицо»);
- `expenseItem` = статья `Зарплата`;
- `counterpartyadjustment` с `agent = employee` — для начислений/корректировок
  долга по зарплате.

То есть «взаиморасчёты» в МойСклад ведутся и по сотрудникам тем же механизмом,
что и по контрагентам. Это прямо ложится на схему заказчика
(`выплата зарплаты → Сотрудник (KPI + зарплата)`).

## 5. Договор (`contract`) и Проект (`project`) — аналитические разрезы

### 5.1. `contract` (Договор)

| Поле | Тип | Смысл |
|---|---|---|
| `contractType` | Enum | `Sales` (купля-продажа) / `Commission` (комиссия). |
| `rewardType` | Enum | `PercentOfSales` (процент от суммы продажи) / `None`. |
| `rewardPercent` | Int | Процент вознаграждения (для комиссии). |
| `agent` | Meta | Контрагент договора. `+Обязательное` |
| `ownAgent` | Meta | Своё юрлицо по договору. `+Обязательное` |
| `sum` | Int | Сумма договора (в копейках). |
| `contractType` / `moment` / `state` / `rate` | — | Тип, дата, статус, валюта. |

В денежном документе — поле `contract` (Meta). В Durov OS отдельной сущности
«договор» пока нет; у клиента есть `contract_file_id`. На `MoneyMovement` можно
завести необязательную ссылку/строку «договор», но в `0011-c` это **не тащим** —
достаточно `source_ref` на клиента.

### 5.2. `project` (Проект)

| Поле | Тип | Смысл |
|---|---|---|
| `name` | String(255) | Наименование. `+Необходимо при создании` |
| `code` / `externalCode` / `description` | String | Прочее. |
| `archived` | Boolean | В архиве. |
| `owner` / `group` / `shared` | — | Доступ. |

Универсальный разрез для сквозной аналитики (все денежные документы имеют поле
`project`). В Durov OS роль «проекта» уже играет **цикл клиента** (`cycles`) и
`production`-проект. Отдельную сущность `project` не заводим; при необходимости
`MoneyMovement` группируется через `source_ref`.

## 6. Единицы, валюта, налог

- **Все денежные суммы в API — в копейках** (целое/Float). `sum = 150000` = 1500 ₽.
  В Durov OS суммы хранятся как `Numeric(14, 2)` в рублях (см. `clients.Client.final_price`) —
  при любом будущем обмене с МойСклад нужен множитель 100. Внутри `MoneyMovement`
  остаёмся в рублях `Numeric(14, 2)`, консистентно с остальным бэком.
- **Валюта** — объект `rate` (`currency` + `value` курса). У Durov OS всё в рублях;
  `MoneyMovement.currency` — строковый код (`"RUB"`), поле-задел, без курсов.
- **Налог** — поле `vatSum` (сумма НДС в документе, копейки). Это и есть «Налог»
  из схемы заказчика. В `MoneyMovement.tax` кладём сумму налога `Numeric(14, 2)`;
  ставку (%) — опционально, отдельным полем, как в МойСклад (`advancePaymentVat`
  на юрлице, ставки НДС — справочник `taxrate`).

| `Supplier.contacts` (JSON) | `counterparty.phone`/`email`/`contactpersons` | |
| `Supplier.status` (`active`/`archived`) | `counterparty.archived` + `counterparty.state` | |
| `Supplier.categories` | `counterparty.tags` | свободные метки направлений |
| **баланс/долг поставщика** (добавляет `0011-d`) | `report/counterparty` → `balance` | вычисляемый, не хранимый в МойСклад; у нас — денормализованное поле, пересчёт при `posted` |

### 7.3. `Supply` — есть черновой (`app/warehouse/models.py`), расширяет `0011-d`

| Поле Durov OS | Источник в МойСклад | Комментарий |
|---|---|---|
| `Supply` (сущность) | `purchaseorder` (заказ поставщику) + `supply` (приёмка) | у нас одна сущность на «поставку»; в МойСклад это два документа |

| `Supply.supplier_id` | `supply.agent` → `counterparty` | |

| оплата поставки | `paymentout`/`cashout` c `operations=[supply.meta]`, `expenseItem`=«Закупка товаров» | создаёт `MoneyMovement(supply_payment)` |

> Принцип PROJECT.md: **оплата и физическая приёмка поставки — независимые
> состояния**. В МойСклад это и есть: `supply.applicable` (приёмка) ≠
> `paymentout.applicable` (оплата). Не связывать один с другим.

### 7.4. `source_ref` — полиморфная привязка (ровно одна)

| Подвид `MoneyMovement` | Поле | Аналог МойСклад |
|---|---|---|
| доход от продажи | `client_id` → `clients.id` | `paymentin.agent` = клиент-`counterparty` + `operations` на его счёт/отгрузку; обновляет «Состояние оплаты» (`Client.is_paid` / `balance_paid`) |
| выплата зарплаты | `employee_id` → `users.id` | `paymentout.agent` = `employee` + `expenseItem`=«Зарплата» |
| оплата поставки | `supply_id` → `supplies.id` | `paymentout.operations` = `[supply.meta]` → `supply.agent` = поставщик |
| прочее | все NULL | платёж без `operations` |

Ограничение (принцип `0011`): **не более одной** привязки на проводку.

### 7.5. Связи с существующими разделами

| Схема заказчика | МойСклад | Durov OS |
|---|---|---|
| `доход от продажи → Клиент (Состояние оплаты)` | `paymentin` + баланс контрагента | `MoneyMovement(sale_income).client_id` → пересчёт `Client.is_paid`/`balance_paid` (`app/clients`) |
| `выплата зарплаты → Сотрудник (KPI + зарплата)` | `paymentout(agent=employee)` + взаиморасчёты по сотруднику | `MoneyMovement(salary_payout).employee_id` → раздел зарплаты (`app/users`) |

## 8. Выводы для `0011-c` (модель `MoneyMovement`)

1. **Направление** (`приход`/`расход`) — из типа документа. Заводим `direction`
   enum (`income`/`expense`) + `subkind` enum (`sale_income`, `salary_payout`,
   `supply_payment`, `tax`, `rent`, `other`). Статью ДДС как настраиваемый
   справочник в MVP не делаем — фиксированный enum по §3.3.
2. **Статусная машина.** `draft → approved → posted → cancelled`.
   - `posted` ⇔ «проведён» (`applicable=true` в МойСклад): деньги/взаиморасчёты
     учтены, запись неизменяема.
   - `draft`/`approved` — наш процессный слой (в МойСклад это `state` + отсутствие
     проведения); `approved` = «согласовано», может рождать/закрывать задачу в
     `tasks`.
   - `cancelled` из `posted` — только с `cancel_reason`; исходную запись не
     удаляем и не редактируем, при необходимости компенсируем отдельной записью
     (аналог `counterpartyadjustment`). История не переписывается (принцип
     PROJECT.md).
3. **«Оценка» (`assessment`).** В МойСклад у денежного документа **нет** поля
   «оценка достоверности» или «план/факт». Ближайшие смыслы:
   - `expenseitem.operatingExpenses` — влияет ли расход на оценку прибыли;
   - разделение «плановое обязательство» (счёт `invoiceout`/`invoicein`, заказ)
     против «фактический платёж».
   Решение для `0011-c`: `assessment` = enum `planned | actual` (по умолчанию
   `actual`) + отдельный boolean `affects_profit` (по умолчанию `true`, аналог
   `operatingExpenses`). Отдельную «шкалу достоверности» не вводим.
4. **Суммы** — `Numeric(14, 2)` в рублях (консистентно с `clients`/`warehouse`).
   Помним: МойСклад отдаёт копейки (×100) — на будущий обмен.
5. **Налог** — `tax` (`Numeric(14, 2)`, сумма) ← `vatSum`. Ставку `%` в MVP
   опускаем или держим необязательным полем.
6. **`initiator`** ← `owner` (сотрудник, `users.id`), обязателен для `posted`.
7. **`source_ref`** — полиморфно, ровно одна из `client_id` / `employee_id` /
   `supply_id`, либо ни одной для `other`. Валидация «не больше одной привязки».
8. **Сознательно НЕ переносим из МойСклад:**
   - нал/безнал (`cashin/out` vs `paymentin/out`), `organizationAccount` /
     `agentAccount`, кассы (`cashier`, `retailStore`) — денежный контур один;
   - `contract` как сущность — достаточно `source_ref`;
   - `project` как сущность — роль проекта играет цикл клиента / производство;
   - `factureIn` / `factureOut`, `commissionreport*`, розничные ордера,
     `prepayment` — вне контура фичи;
   - `state` как настраиваемый справочник статусов — заменяем фиксированной
     статусной машиной из п. 2;
   - множественные `operations` с `linkedSum` — у нас одна привязка `source_ref`
     на проводку.
