## 1. Документы движения денежных средств

В МойСклад нет отдельной сущности «проводка». Движение денег — это **финансовые
документы**. Каждый из них — приход или расход, безнал или нал:

| Сущность API | Русское имя | Направление | Канал | Назначение |
|---|---|---|---|---|
| `paymentin` | Входящий платёж | приход (+) | безнал (банк) | деньги пришли на расчётный счёт: оплата от клиента, возврат от поставщика |
| `paymentout` | Исходящий платёж | расход (−) | безнал (банк) | деньги ушли со счёта: оплата поставщику, налоги, **выплата зарплаты**, аренда |
| `cashin` | Приходный ордер | приход (+) | нал (касса) | деньги пришли в кассу |
| `cashout` | Расходный ордер | расход (−) | нал (касса) | деньги выданы из кассы (в т. ч. зарплата наличными) |
| `counterpartyadjustment` | Корректировка взаиморасчётов | ± | — | ручная правка баланса контрагента/сотрудника без реального движения денег |
| `prepayment` / `prepaymentreturn` | Предоплата / возврат предоплаты | ± | — | розница: предоплата по заказу и её возврат |
| `retaildrawercashin` / `retaildrawercashout` | Внесение/выплата (розн. смена) | ± | нал (ДС розницы) | движение по денежному ящику розничной смены |

Для контура Durov OS релевантны первые четыре. Различие нал/безнал (`cashin`/`cashout`
против `paymentin`/`paymentout`) у нас **не воспроизводим** — в Durov OS денежный
контур один. Берём объединённую семантику: «приход» ↔ `paymentin`/`cashin`,
«расход» ↔ `paymentout`/`cashout`.

### 1.1. Ключевые поля денежного документа (дословно из API)

Общие для `paymentin` / `paymentout` / `cashin` / `cashout`:

| Поле | Тип | Смысл |
|---|---|---|
| `sum` | Float | Сумма платежа **в копейках**, в валюте документа. `+Обязательное при ответе` |
| `vatSum` | Float | Сумма НДС (в копейках). `+Обязательное при ответе` |
| `rate` | Object | Валюта + курс (`{currency: Meta, value, ...}`). `+Обязательное при ответе` |
| `moment` | DateTime | Дата документа. `+Обязательное при ответе` |
| `applicable` | Boolean | **Отметка о проведении** (см. §2). `+Обязательное при ответе` |
| `state` | Meta → `state` | Пользовательский статус документа (см. §2). `+Expand` |
| `agent` | Meta | Контрагент. Для `paymentout`/`cashout` — «контрагента, **сотрудника** или юр.лицо». `+Обязательное при создании` |
| `organization` | Meta | Своё юрлицо (от кого/кому). `+Обязательное при создании` |
| `paymentPurpose` | String | Назначение платежа (текст). |
| `operations` | Array(Meta) + `linkedSum` | Привязка платежа к базовым документам (§4.3). |
| `project` | Meta → `project` | Проект — аналитический разрез (§5). `+Expand` |
| `contract` | Meta → `contract` | Договор (§5). `+Expand` |
| `owner` | Meta → `employee` | **Владелец (Сотрудник)** — кто завёл документ. `+Expand` |
| `group` | Meta | Отдел. |
| `name` | String | Номер документа. |
| `description` | String(4096) | Комментарий. |
| `created` / `updated` / `deleted` | DateTime | Служебные даты. `+Только для чтения` |

Только у **безналичных** (`paymentin` / `paymentout`):

| Поле | Тип | Смысл |
|---|---|---|
| `organizationAccount` | Meta → `account` | Расчётный счёт своего юрлица. `+Expand` |
| `agentAccount` | Meta → `account` | Расчётный счёт контрагента. `+Expand` |
| `incomingNumber` | String(255) | Входящий номер (номер платёжного поручения). |
| `incomingDate` | DateTime | Входящая дата. |

Только у **расходных** (`paymentout` / `cashout`):

| Поле | Тип | Смысл |
|---|---|---|
| `expenseItem` | Meta → `expenseitem` | **Статья расходов / статья ДДС** (§3). Обязательна при проведении. |
| `noClosingDocs` | Boolean | «Без закрывающих документов». |

> У приходных (`paymentin` / `cashin`) поля `expenseItem` **нет** — доход в МойСклад
> не разбивается по статье расхода; его «вид» определяется типом документа и
> привязкой `operations` (к какому заказу/отгрузке относится приход).

Только у `paymentin` / `cashin`: `factureOut` (счёт-фактура выданный);
у `paymentout` / `cashout`: `factureIn` (счёт-фактура полученный).

## 2. Проведение (`applicable`) против статуса (`state`)

Это два **независимых** признака — ключевой факт для статусной машины `0011-c`.

- **`applicable`** (Boolean) — «Отметка о проведении».
  - `false` → документ существует как **черновик**: он не влияет на остаток денег
    и не двигает взаиморасчёты.
  - `true` → документ **проведён**: сумма учтена в остатке ДС, баланс контрагента
    (или сотрудника) пересчитан, приход/расход попал в отчёты (ДДС, «Прибыли и
    убытки»).
  - Это переключаемый флаг: провёл → распровёл. Отдельного значения «отменён» у
    документа нет — «отмена» в МойСклад = либо распроведение (`applicable=false`),
    либо удаление (`deleted`), либо компенсирующая `counterpartyadjustment`.
- **`state`** (Meta → сущность `state`) — **пользовательский статус** документа из
  настраиваемого списка (например «Ожидает оплаты», «Оплачен», «Согласование»).
  У `state` есть `stateType` (`Regular` / `Successful` / …), `name`, `color`,
  `entityType`. `state` — это визуально-процессный ярлык; **сам по себе денег не
  двигает**, двигает только `applicable`.

### 2.1. Проекция на статусную машину `MoneyMovement` (`0011-c`)

Родитель `0011` задаёт: `draft → approved → posted → cancelled` (только вперёд +
`cancelled`; `posted` не редактируется).

| Статус Durov OS | Эквивалент в МойСклад |
|---|---|
| `draft` | документ создан, `applicable = false`, `state` = «Черновик»/«Согласование» |
| `approved` | `applicable = false`, `state` = «Согласовано» (согласование в Durov OS — это наш слой поверх `state`; в МойСклад отдельного шага нет) |
| `posted` | `applicable = true` — проведён, деньги/взаиморасчёты учтены; редактирование запрещаем (в МойСклад проведённый редактируется, но мы ужесточаем — см. принцип PROJECT.md «оплата — независимое состояние») |
| `cancelled` | `applicable = false` + пометка причины; при уже проведённом — компенсирующая запись по образцу `counterpartyadjustment`, исходный документ не удаляем (история не переписывается) |

Вывод: **`applicable` — это граница `posted`**. Шаги `draft`/`approved` — наш
процессный слой (аналог `state` + задача на согласование из раздела `tasks`).
