# Закупки → Контрагенты: спецификация следующего этапа

Дата: 18.11.2026. Статус: требования для бэклога; функциональность этого документа ещё не реализована. Последовательность выпуска: после первого выпуска «Диска». Дизайн-система и действующие интеграции сохраняются.

## 1. Результат для сотрудников

«Поставщики» переименовываются в «Контрагенты». Одна карточка объединяет реквизиты, контакты и связанные закупочные документы. Поставщик остаётся ролью контрагента: переименование не должно превращать каждого клиента или сотрудника в поставщика. В выборе поставщика заказа показываются только контрагенты с соответствующей ролью.

Данные из МойСклада заполняют пустые поля. Отличающиеся заполненные значения показываются на сравнении и заменяются только после явного выбора пользователя. Все изменения сохраняют автора, источник и прежнее значение. Исправление реквизитов карточки не переписывает уже проведённые документы.

## 2. Что уже есть в коде и что необходимо сохранить

- `app/accounting/models.py`: `Counterparty` — бухгалтерский справочник; `CounterpartyKind` задаёт деловую роль, а не юридическую форму. Есть ссылки на клиента/поставщика, ИНН, признак активности и платежи.
- `app/warehouse/models.py`: `Supplier` — закупочный профиль, контакты, категории, цены, MAX и существующие идентификаторы. Его используют заказы и приёмки.
- `app/accounting/router.py`: действующие CRUD `/counterparties` и `/counterparties/{id}/payments` внутри бухгалтерского приложения. Их контракты сохраняются.
- `app/moysklad/models.py`: `SourceRecord`, `SourceLink`, `ImportRun` — снимки источника, сопоставления и история импорта. Расширить их использование, не создавать второй несогласованный импортёр.
- `app/moysklad/service.py` уже различает `invoicein` («Счета поставщиков») и `facturein` («Счета-фактуры полученные»). Использовать это разделение; наличие типа в коде ещё не подтверждает полноту загруженных документов.
- `app/moysklad/importer.py`: присваивание `obj.inn = raw.get('inn') or obj.inn` может заменять заполненный локальный ИНН. Исправление обязательно для фонового, пакетного и ручного импорта. Поиск только по имени не даёт основания автоматически объединять карточки.
- Сейчас модель допускает не более одной связи client/supplier. Совмещение ролей требует явной миграции и изменения сервисной проверки; одного нового поля на экране недостаточно.

Сохраняются существующие ID/FK, `source_id`, `SourceLink`, маршруты старых карточек, цены, статусы заказов, платежи, связи с MAX и права. Старый URL поставщика открывает ту же карточку через совместимый маршрут; новый пункт меню не дублируется. Бухгалтерский справочник и закупочный экран используют один сервис реквизитов.

## 3. Форма и правила заполнения

Карточка: «Реквизиты», «Документы», «История». На широком экране поля располагаются в две колонки, адреса — на всю ширину; на телефоне — в одну колонку. Используются текущие Input, Select, Tabs, Dialog, кнопки, типографика и интервалы. Новую палитру и сторонний набор компонентов не вводить.

| Блок / поле | Хранение и обязательность | Поведение |
|---|---|---|
| Наименование | `name`, строка до 255; обязательно | Существующее поле сохраняется; для физлица допускается ФИО |
| Тип контрагента | `legal_type`: `legal_entity`, `sole_proprietor`, `individual`; обязательно для новой карточки | Выбор без заранее проставленного «Юрлицо»; не заменяет деловую роль |
| ИНН | Строка, обязательна для новой карточки | 10 цифр для юрлица, 12 для ИП/физлица; контрольные разряды, поиск дублей; ведущие нули сохраняются |
| КПП | Строка 9 знаков; только юрлицо | Проверка действующего формата ФНС; не вводить глобальную уникальность КПП |
| ОГРН | Строка 13 цифр; только юрлицо | Проверка длины и контрольного разряда, конфликта с другой организацией |
| Расчётный счёт | Дочерняя запись банковского счёта; 20 цифр для рублёвого счёта РФ | Допускается несколько счетов; один основной. При добавлении счёта обязательны номер, БИК и название банка |
| БИК | Строка 9 цифр | Формат и проверка контрольного ключа счёта вместе с БИК; заполнение банка из справочника только при наличии действующего подключения |
| Банк | Наименование; корреспондентский счёт; адрес банка необязателен | Коррсчёт при заполнении — 20 цифр и проверка в паре с БИК; не подставлять фиктивный счёт при отсутствии |
| Юридический / фактический адрес | Две самостоятельные строки и исходные структурированные данные импорта | Для физлица/ИП пояснение «Адрес регистрации» при сохранении того же поля данных |
| Адреса совпадают | `addresses_same`, boolean | Включение копирует юридический адрес в фактический. Последующее ручное изменение любого адреса снимает флаг; второй адрес при этом не меняется. Совпадение строк само не включает флаг |
| Директор | `director_full_name`, строка | Для юрлица; ИП/физлицу не приписывать директора автоматически |
| Контактное лицо | ФИО, телефон, email в `counterparty_contacts` | Один основной контакт в форме, дополнительные допускаются. Общий телефон организации не выдавать за телефон конкретного человека |

КПП, ОГРН, адреса и контакты в этом этапе не становятся безусловно обязательными для сохранения: пользователь явно потребовал обязательный ИНН. Полнота данных для конкретного документа/платежа проверяется отдельно. Новую карточку можно сохранить без банковского счёта; частично заполненная строка счёта требует исправления или удаления.

Формат проверяется и в браузере, и на сервере. Телефон нормализуется с сохранением исходного представления, email проверяется без проверки «существования ящика». Ошибки после сохранения: красная рамка, текст у поля, `aria-invalid`, фокус на первой ошибке; цвет не служит единственным сигналом. Пока идёт сохранение, повторный клик блокируется. При ошибке данные формы сохраняются.

При смене типа на ИП/физлицо КПП и ОГРН скрываются. Если они уже были заполнены, перед сохранением показать, что они будут исключены из действующих реквизитов; прежние значения остаются в истории. Отмена смены типа возвращает введённое. ОГРНИП, полученный из источника, хранится отдельно как исходное значение; его нельзя записывать в ОГРН юрлица. Расширение формы ОГРНИП — отдельная небольшая задача при необходимости.

## 4. Уникальность и модель данных

ИНН идентифицирует налогоплательщика; КПП уточняет постановку организации на учёт. ИП использует ИНН физлица. Поэтому одинаковый КПП сам по себе не означает дубль, а ИП и то же физлицо не следует автоматически считать двумя разными людьми. Основание: [разъяснение ФНС об ИНН](https://www.nalog.gov.ru/rn77/fl/interest/inn/). Проверки формата сверяются с [приказом ФНС № ЕД-7-14/559@](https://www.nalog.gov.ru/rn77/about_fts/docs/16581721/), действующим с 01.01.2026.

Предлагаемая модель: один основной контрагент на подтверждённый ИНН; филиалы/регистрации — дочерние записи с КПП. Повтор ИНН предлагает открыть существующую карточку, добавить роль или регистрацию; не создаёт скрытый дубль. ИП и физлицо с одним ИНН требуют явного выбора профиля и сохранения истории статуса. Автоматического слияния исторических карточек в этом выпуске нет.

| Сущность | Основные поля и ограничения |
|---|---|
| `counterparties` (расширение) | Существующий `id`, `name`, `inn`, legacy `kind`, ссылки и активность; новые `legal_type`, `ogrn`, адреса, `addresses_same`, директор, `version`, `completion_status`, основной contact/account/registration. Новые поля на первом шаге nullable |
| `counterparty_registrations` | `id`, `counterparty_id`, `kpp`, адрес, `is_primary`, source ID, версия; UNIQUE(counterparty_id, kpp), не UNIQUE(kpp). Основной КПП выводится в простую форму |
| `counterparty_roles` | `counterparty_id`, `role`; UNIQUE пары. Разрешает supplier и client одновременно; legacy `kind` сохраняет прежнюю основную роль до перевода потребителей и не меняется от порядка импорта |
| `counterparty_bank_accounts` | `id`, `counterparty_id`, номер, БИК, банк, коррсчёт, адрес, валюта, основной/архивный, source ID, версия, статус проверки и основание. UNIQUE(counterparty_id, bik, account_number). Не использовать таблицу банковских счетов нашей организации |
| `counterparty_contacts` | `id`, `counterparty_id`, ФИО, должность, телефон, email, основной/архивный, source ID, версия. Контакты без ФИО допустимы как общие реквизиты организации |
| Сопоставления источников | Существующий `SourceLink` + идентификатор подключения/аккаунта источника при поддержке нескольких подключений. Нельзя сопоставлять ID разных аккаунтов МойСклада как один объект |
| История / доказательства | Поле, прежнее/новое значение, автор, время, запрос, причина, source ID + хеш снимка, при ручной проверке — ссылка на файл/документ и проверяющий. Неизменяемые записи через общий механизм аудита |
| Предпросмотр синхронизации | `preview_id`, контрагент, версия локальных данных, снимок/хеш источника, изменения, ошибки, срок действия, автор; не создаёт бухгалтерских движений |

После очистки существующих дублей добавить ограничения БД для непустого нормализованного ИНН и ОГРН. До этого выдавать отчёт конфликтов и блокировать создание новых дублей сервисом с защитой от одновременного создания. Архивная карточка тоже участвует в проверке: вместо дубля предложить восстановление. Не менять ИНН контрагента с проведёнными документами как обычное исправление: отдельная проверка бухгалтером, причина и подтверждающий документ; другой налогоплательщик — новая карточка.

Все бизнес-изменения увеличивают версию карточки и пишут историю в одной транзакции. `version` обязателен при редактировании; устаревшая версия даёт 409 и экран сравнения. Повтор запроса с тем же `request_id` и содержимым возвращает прежний результат; другой payload с тем же ключом — 409.

## 5. Документы контрагента

Источники вкладки: приёмки, заказы поставщику, входящие счета-фактуры, исходящие платежи. Для счетов-фактур нужны реальные тип и данные: обычный счёт на оплату и приёмка не должны переименовываться в счёт-фактуру. Если полноценной локальной карточки ещё нет, показать доступный импортированный документ с явной пометкой источника и рабочим переходом в МойСклад; отсутствие импорта показать как статус, а не пустой успешный результат.

Связи: контрагент → закупочный профиль `supplier_id` → заказ → приёмки; платежи — по прямой `counterparty_id` и существующим связям заказа/распределений. Счёт-фактура связан с контрагентом и первичными документами через реальный источник. Несколько связей одного платежа не создают несколько строк. Ключ строки — локальная сущность/id либо подключение/тип/source_id; импортированное представление локального документа не выводится повторно.

Колонки: тип, номер, дата документа, сумма, валюта, статус, источник и действие «Открыть». Статус проведения и пользовательский статус показываются отдельно, если они различаются. Суммы — Decimal/копейки, не float; приёмки/заказы/платежи не складываются в общий «оборот», чтобы не учитывать одно обязательство несколько раз. Итоги допускаются по типу и валюте с указанным смыслом.

Фильтры: один/несколько типов, дата от/до включительно, поиск по номеру. Серверная сортировка дата DESC + ID и пагинация; переход назад восстанавливает фильтры. Строка открывает конкретный документ в один клик. Проверка прав на сами документы обязательна: доступ к справочнику не даёт доступ к бухгалтерии. Недоступные реквизиты и суммы не попадают ни в ответ API, ни в экспорт.

Excel (`.xlsx`) и CSV выгружают все строки выбранного фильтра, а не текущую страницу, с теми же правами и порядком. Крупная выгрузка — фоновое задание с прогрессом и ограниченным сроком скачивания. CSV UTF-8 с BOM; защита значений от выполнения формул; ИНН/счета в Excel — текст, даты и суммы — типизированные значения, валюта отдельной колонкой. Пустая выборка выгружается с заголовками.

## 6. Обмен с МойСкладом

Использовать существующий серверный коннектор REMAP 1.2. Новый коннектор и новый комплект паролей для этого этапа не нужны. Убедиться, что действующий сервисный доступ читает контрагентов, их счета/контакты и нужные виды документов. Токен не передаётся браузеру.

В официальной модели контрагента предусмотрены юридический тип, ИНН/КПП/ОГРН, отдельный ОГРНИП, адреса и контакты; банковские счета и контактные лица доступны связанными ресурсами. Маппинг адаптера сверяется с [моделью Counterparty](https://github.com/moysklad/remap-1.2-php-sdk/blob/master/docs/Model/Counterparty.md) и [API Counterparties](https://github.com/moysklad/remap-1.2-php-sdk/blob/master/docs/Api/CounterpartiesApi.md). Не считать объект `meta` полным содержимым коллекции: загружать все страницы счетов и контактных лиц.

| Наше поле | Источник / правило |
|---|---|
| Тип | `companyType`, явное сопоставление enum по актуальной схеме; неизвестное значение — конфликт, не молчаливое «юрлицо» |
| ИНН / КПП / ОГРН | `inn` / `kpp` / `ogrn`; нормализация и проверка до применения |
| Адреса | `legalAddress`, `actualAddress`; структурированные варианты сохраняются рядом, без потери исходного текста |
| Счета | `/entity/counterparty/{id}/accounts`: номер, bankCode/БИК, bankName, correspondentAccount, доступный адрес банка |
| Контактные лица | `/entity/counterparty/{id}/contactpersons`; общие `phone`/`email` отдельно, без придумывания ФИО |
| Директор | Только однозначно настроенный атрибут/подтверждённый контакт. Владелец карточки (`owner`) не является директором |

Последовательность ручного обновления:

1. Нажатие «Обновить данные из МойСклад» загружает предпросмотр; базу реквизитов пока не меняет.
2. Сопоставление прежде всего по существующему `SourceLink`. Если его нет — кандидаты по проверенному ИНН и регистрации; неоднозначность требует выбора. Название даёт подсказку, но не автоматическое объединение.
3. Диалог показывает столбцы «Поле / У нас / В МойСклад / Действие», дату источника и полноту загрузки. Пустые локальные поля с валидным источником выбраны для заполнения; отличающиеся непустые значения не выбраны. Одинаковые значения обозначаются «Без изменений».
4. Пользователь подтверждает кнопкой «Применить выбранное». Замена непустого поля требует отдельного выбора и фиксируется в истории. Непустое включает намеренно заданные значения; пробелы нормализуются до проверки пустоты, `false`/0 не считаются отсутствием.
5. Сервер сверяет права, локальную версию, актуальность снимка источника и версии дочерних записей. Изменения после предпросмотра → 409, предложить новое сравнение; не применять частично устаревшее решение.
6. Все выбранные изменения, provenance и результат запроса сохраняются атомарно. Показывается число заполненных/заменённых/пропущенных полей; карточка обновляется без перезагрузки.

Пустое значение источника никогда не стирает локальное. Удалённый в источнике контакт/счёт автоматически не удаляется. Архивирование контрагента в источнике показывается отдельным предложением и не заменяет локальный статус без подтверждения. Совпадение банковского счёта определяется source ID, затем номером+БИК; одинаковый телефон не объединяет разных людей. Существующие основной счёт/контакт не переключаются импортом. Несовпадение ИНН при установленной связи блокирует применение всей карточки до проверки идентичности.

У ручного, ретроспективного и фонового импорта единая политика fill-empty. 401/403 — понятная проблема доступа; 429/сетевая ошибка — ограниченные повторы с задержкой и статус «Данные не обновлены». При неполной загрузке хотя бы одной требуемой коллекции предпросмотр нельзя выдать за полный; применение либо блокируется, либо явно ограничивается успешно загруженным блоком по подтверждению. Никаких обратных PUT/PATCH в МойСклад в этом этапе.

## 7. Проверка реквизитов и права

Загрузка из МойСклада означает «получено из источника», а не «подтверждено банком/ФНС». Для банковских реквизитов: `unverified` → `pending_review` → `verified`/`rejected`; проверяющий, дата и основание обязательны для verified. Скан карточки предприятия/официальное письмо прикрепляется через существующее защищённое хранилище с правами и контрольной суммой. История доступна уполномоченным пользователям; секреты подключения в неё не попадают.

Предлагаемые разрешения: просмотр справочника; редактирование общих полей; предложение реквизитов; подтверждение банковских реквизитов; синхронизация; просмотр/экспорт документов. Закупщик ведёт карточку и предлагает изменения. Татьяна в роли бухгалтера проверяет банковские реквизиты и основания; руководитель видит всё в пределах общей модели доступа и утверждает спорные решения. Назначения проверяются по действующим учётным записям, а не по совпадению имени.

Новый/изменённый счёт не наследует доверие старого. Изменение ИНН, получателя, номера счёта или БИК отменяет применимость прежнего разрешения на автооплату до повторной проверки. Проверенность поставщика, согласованная продажа/техкарта и цена не выше предыдущей остаются отдельными условиями автоматической оплаты. Заполнение формы само не разрешает платёж.

Снимок реквизитов, использованных в согласованном/проведённом документе и платеже, остаётся неизменным. Черновик при изменении реквизитов показывает различие и требует повторного подтверждения перед оплатой.

## 8. API-контракт для реализации

Базовый путь существующего бухгалтерского приложения — `/api/accounting` (mount в `app/main.py`); нижеследующие пути относительные. Добавить поля в существующие DTO совместимо. Пагинированный ответ нового реестра выделить в новый endpoint, не менять существующий список на объект без версии API. Новая форма создания использует контракт v2 с обязательным ИНН. Старый POST сохраняет контракт для действующих интеграций, но неполная запись получает `needs_completion`, не считается проверенной и не допускает автооплату; источник такого создания виден в отчёте. Это исключение для совместимости, а не способ обхода проверки новой формы.

| Метод / путь | Запрос → результат |
|---|---|
| GET `/counterparties/registry` | `q, role, legal_type, completion_status, include_inactive, offset, limit` → `items, total, permissions` |
| POST `/counterparties/v2` | Основные поля с обязательным ИНН и типом, контакты/счета, request_id → карточка и version; старый POST обслуживается совместимым адаптером |
| GET `/counterparties/{id}` | Реквизиты, роли, счета/контакты, provenance, version, permissions, completeness |
| PATCH `/counterparties/v2/{id}` | Изменённые поля, version, request_id, основание → обновлённая версия |
| POST `/counterparties/validate-identity` | Тип, ИНН, КПП, ОГРН, исключаемый ID → ошибки по полям/разрешённые ссылки на кандидатов; это подсказка, не замена проверки при сохранении |
| POST/PATCH `/counterparties/{id}/accounts[/{account_id}]` | Реквизиты, версии, request_id → счёт с состоянием проверки |
| POST `/counterparties/{id}/accounts/{account_id}/verify` | Решение, версия, evidence_id, причина → проверенный/отклонённый счёт, аудит |
| POST/PATCH `/counterparties/{id}/contacts[/{contact_id}]` | Контакт, версии, request_id → контакт |
| GET `/counterparties/{id}/documents` | `types[], date_from, date_to, q, offset, limit` → строки с типом/номером/датой/суммой/валютой/статусом и безопасной ссылкой, total, полнота источников |
| POST `/counterparties/{id}/documents/export` | Фильтры, format=xlsx/csv → файл либо job_id; скачать результат может только уполномоченный инициатор |
| POST `/counterparties/{id}/moysklad/preview` | Идентификатор подключения при необходимости → preview_id, поля/конфликты, локальная версия, дата источника, срок действия |
| POST `/counterparties/{id}/moysklad/apply` | preview_id, выбранные изменения, version, request_id → результат и новая карточка |
| GET `/counterparties/{id}/history` | Курсор → изменения с источниками и основаниями |
| POST `/counterparties/backfill/preview`, `/apply` | Административный запуск fill-empty: план/подтверждение → job_id |
| GET `/counterparties/jobs/{id}` | Статус, прогресс, ошибки, счётчики; без утечки чужих выгрузок |

Статические маршруты registry/v2/validate-identity/jobs регистрируются до `/{id}`. 401 — нет сессии, 403 — нет действия, 404 — недоступный объект, 409 — дубль/версия/устаревший предпросмотр, 422 — поля с ошибками; ответ содержит машинный код и понятное русское сообщение. GET не изменяет данные. Исторический PATCH проходит через тот же сервис без молчаливого перезаписывания реквизитов: новые критичные операции и проверка версии включаются отдельным контрактом v2; старые разрешённые поля остаются совместимыми.

События: смена типа, ручное изменение адреса, сохранение, синхронизация, подтверждение счёта, изменение фильтра, экспорт. После мутации обновляются карточка, список и permissions; ошибка не сбрасывает форму. Серверные события аудита: `counterparty.updated`, `counterparty.sync_applied`, `counterparty.account_verification_changed`, `counterparty.backfill_completed`; повтор запроса не порождает второе событие.

## 9. Миграция и ретроспективное заполнение

1. Сделать резервную копию и отчёт: количество карточек, пустые ИНН, дубли, несогласованные связи supplier/client, наличие счетов-фактур и необходимых коллекций в снимках МойСклада.
2. Аддитивно добавить nullable-поля, дочерние таблицы и версии. Существующие карточки доступны сразу; неполные помечаются «Нужно дополнить», не получают вымышленных значений.
3. Привязать закупочные профили к реестру по уже подтверждённым связям. Неоднозначности — отдельная очередь. До решения связи старые документы доступны по прежним маршрутам.
4. Предпросмотр пакетного заполнения: что заполнится, конфликтует, отсутствует. Подтверждённый запуск меняет только пустые поля; одна карточка — одна транзакция, сбой не теряет прогресс; повтор идемпотентен. Сохраняется отчёт и provenance.
5. Ввести новые ограничения после разрешения конфликтов. ИНН обязателен при создании новых карточек через новый рабочий процесс; старые неполные карточки можно просматривать, архивировать и дополнять. Новый платёж по неполным/непроверенным банковским данным не проходит.
6. Проверить совместимость на копии базы, затем включить новый экран. При откате интерфейса не удалять новые таблицы/аудит/вложения; безопасное выключение функции предпочтительнее обратной потери данных.

## 11. Зависимости и ограничения

- Основная реализация использует существующий МойСклад; дополнительные подключения не обязательны. До оценки сроков нужны read-only инвентаризация данных и проверка прав коннектора на счета/контакты/счета-фактуры.
- Директор и адрес банка могут отсутствовать в источнике. Тогда честно показать незаполненное поле; требуется ручной документ или согласованное сопоставление атрибута.
- Автозаполнение по ИНН из ФНС, проверка статуса организации и обновляемый справочник БИК — дополнительные интеграции, не подменяются проверкой длины номера. В базовом этапе достаточно проверки формата, источника и документального подтверждения бухгалтером.
- Если счета-фактуры ещё не загружены, CP-06 включает адаптер этого реального типа и карточку/переход; наличие приёмок не считается выполнением требования о счетах-фактурах.
- Сканы и снимки подтверждают происхождение значений; журнал хешей не объявляется независимым блокчейном. Нужны совместные резервные копии базы, файлов и истории.

Готовность этапа означает работающую форму, четыре вида документов с корректной полнотой, оба экспорта, ручную и ретроспективную синхронизацию, сохранённые интеграции и пройденную приёмку. Одно переименование вкладки не считается завершением.
